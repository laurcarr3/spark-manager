spark-manager

Local model management for the NVIDIA DGX Spark. TypeScript monorepo with a CLI and an HTTP API.

Snapshot date: 2026-10-13. Branch main at 4018fd5. Items with the tag UNCOMMITTED come from changes in the working tree that are not committed.

Summary

spark-manager starts, stops, and monitors local LLM serving "recipes" on one DGX Spark. Each recipe is a git checkout. Each recipe has ./start.sh, ./stop.sh, and ./start.sh ps. The recipes run their models in Docker containers.

spark-manager does not know how a recipe serves its model. It only calls the recipe scripts. It keeps one model on the GPU at a time. The author made it to use with a fork of sparkDash.

System design

Core concepts

ConceptDescription
Registered model{ displayName, workspaceDirectory }. The display name is the key in registry.json. Lookup is exact and case-sensitive.
WorkspaceA recipe checkout. Core checks that it is a directory and resolves it with realpath.
Model commandA recipe script. Core runs it as a child process with cwd set to the workspace. Default commands: status ./start.sh ps, start ./start.sh, stop ./stop.sh.
CommandResult{ exitCode, signal, stdout, stderr }. Script failures are returned as data. They are not thrown.
Running modelDetected live from Docker. A container belongs to a workspace if its Compose label com.docker.compose.project.working_dir or one of its mount sources is in the workspace. No "running" state is stored.
Lifecycle lockDirectory lifecycle.lock next to the registry. mkdir is atomic. A pid file lets core remove a stale lock. Core tries up to 4 times.

Model switch flow

startRegisteredModel (packages/core/src/index.ts:85) UNCOMMITTED holds the single-model rule. The CLI and the API both call it.

  1. Make sure that the display name is in the registry. If not, throw UnknownModelError.
  2. Get the lifecycle lock. If a live process holds it, throw an error. Do not wait.
  3. If the registry has other models, ask Docker which registered models are running. Remove the requested model from that list.
  4. If other models are running, call confirmSwitch(runningModels). If the callback is missing or returns false, return { outcome: "cancelled" }.
  5. Stop each running model in sequence. Call onStopping first. If a stop script fails, return { outcome: "stop-failed" }.
  6. Run the start script. Return { outcome: "started", result, stoppedModels }.
  7. Release the lock in finally.
OutcomeCLI resultAPI result
cancelledStart cancelled., exit 1409 MODEL_ALREADY_RUNNING with runningModels
stop-failedUnable to start "Y" because "X" could not be stopped., exit code of the stop script502 COMMAND_FAILED with command
started, script failedExit code of the start script502 COMMAND_FAILED

Design decisions

1. Display names in a registry, not workspace paths

Commit 5397c55. Users type short, stable names. The paths stay in one file. The registry also defines which models the single-model rule checks.

Evidence: packages/core/src/index.ts:219-262.

2. Recipe scripts are the contract

spark-manager only calls start.sh, stop.sh, and start.sh ps. It does not know if a recipe uses SGLang, vLLM, or another server. You can add a new recipe without code changes.

Evidence: default commands at packages/core/src/index.ts:81-83.

3. No shell

Core uses spawn(..., { shell: false }) and execFile("docker", ...). Names and paths cannot inject shell commands.

Evidence: packages/core/src/index.ts:185-190, :389; README "without invoking a shell".

4. Get the running state from Docker, do not store it

Core asks Docker each time. A stored "running" flag cannot go out of date. Core matches containers by the Compose working-directory label or by bind mounts in the workspace.

Evidence: packages/core/src/index.ts:264-385.

5. One model at a time, with confirmation

The DGX Spark has one GPU with unified memory. Two large models compete for that memory. The switch decision is a callback, so each front end sets its policy: the CLI asks the user, and the API needs switchRunning: true. With no callback, core does not switch.

Evidence: commit 0ea543d; packages/core/src/index.ts:103-108.

6. Directory lock serializes start operations

mkdir is atomic on the local file system. The pid file lets a new process find and remove a stale lock. A second start fails at once. It does not wait.

Evidence: packages/core/src/index.ts:413-462.

7. Shared logic in core, thin front ends UNCOMMITTED

The current refactor moves the switch and lock logic from the CLI into core. The CLI and the API now give the same behavior. Core does not write to the console. It sends output through onStdout, onStderr, and onStopping callbacks.

8. Expected outcomes are data, faults are exceptions

Script failures return a CommandResult. Switch results return a discriminated union. Only real faults throw. UnknownModelError is typed, so the API can map it to 404.

Evidence: packages/core/src/index.ts:47-70.

9. Dependency injection for tests

All core functions accept an optional registryPath and command. The API exports a createApp factory. Tests put a fake docker script on PATH.

10. Hardened local API

The API listens on loopback only. POST routes need a JSON content type, so a cross-origin HTML form cannot start or stop a model. The body limit is 8 KB. Body fields are on an allowlist. The bearer token check uses timingSafeEqual. x-powered-by is off.

Evidence: packages/api/src/app.ts:27-29, :233-273; README lines 76-79.

Gaps and risks

README API examples use the wrong name case

The curl examples use DeepSeek-v4. The registry key is deepseek-v4, and lookup is case-sensitive. These examples return 404.

Stop does not take the lock

A stop can run at the same time as a start or a switch.

A held lock gives HTTP 500

The lock error is a plain Error. The API returns 500 INTERNAL_ERROR. A 409 or 423 status is more correct.

API start waits for the full script

The request has no timeout and no streaming. If a recipe runs start.sh in the foreground, the request does not end.

One bad entry or a Docker fault blocks all starts

Detection resolves every workspace and calls Docker. If more than one model is registered, a fault in either step stops every start.

Detection blind spots

Core does not find a container that has no Compose label and no mount in the workspace (for example, only a shared model cache). If the requested model already runs, core runs start.sh again.

Small items

  • Model and ModelStatus types are not used.
  • An empty display-name key gives an incorrect error message about workspaceDirectory.
  • The API does not validate the port. Number() can return NaN.
  • The API does not check the Host header. Without a token, DNS rebinding can reach the API.
  • The CLI version is fixed at 0.0.0.
  • registry.example.json has absolute paths for one user.
  • No linter, formatter, or CI.
